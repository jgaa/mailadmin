# Mailadmin staging and deployment

Run from the repository root. These playbooks target Debian 12/13 over SSH and
become root for host provisioning. They do not run from the HTTP service.
The requirements and takeover boundaries are in [mailserver.md](../../doc/mailserver.md).

## Controller and image

Install ansible-core >= 2.16 and the collection. For rootless local image builds,
install Buildah and its namespace/storage/network helpers:

```bash
sudo apt install buildah uidmap fuse-overlayfs slirp4netns
```

Build and export the image:

```bash
ansible-galaxy collection install -r deploy/ansible/requirements.yml
./deploy/build-image.sh
```

Run the build script on the local development/controller machine. It builds and
tests `mailadmin:staging`, then atomically saves the image to
`~/.local/state/mailadmin/images/staging.tar` (or `$XDG_STATE_HOME` when set).
Both image tag and archive path can be supplied as its first and second arguments.
For the checked-in staging inventory, use the default path or override
`mailadmin_image_archive` to match a custom path.
The script prefers Buildah and exports a Docker-compatible archive without a
Docker daemon. It explicitly uses slirp4netns for rootless networking. An
accessible Docker engine is also supported; select a backend with
`MAILADMIN_BUILDER=buildah` or `MAILADMIN_BUILDER=docker` when needed.

The image build fetches yahat and logfault sources from GitHub. It uses Debian's
prebuilt Boost, Connector/C, OpenSSL and zlib dependencies. Runtime images contain
the application and runtime packages, not development headers or static libraries.
The Docker build targets `mailadmin` specifically; dependencies are not installed
as SDKs in the runtime image.

Do not compile sources or build images on staging. Staging receives a finished
image archive, or later pulls an image built by GitHub Actions. The container
uses Debian 13 for yahat's `std::format` requirement; the Docker host may be Debian
12 or 13. `inventory.staging.yml` targets the supplied `ssh staging` alias.

Copy `inventory.example.yml` to a private inventory outside the repository and
replace the hostname, SSH user and image archive path. Leave the initial
`mailadmin_start_service: false`. Use a disposable, isolated staging machine for
`mailadmin_mode: staging` and `mailadmin_initialize_staging: true`.

For existing production, use a separate inventory with `mailadmin_mode: existing`
and `mailadmin_initialize_staging: false`. Never run staging initialization there:
it changes Courier authentication configuration. Host provisioning can install
packages and trigger their normal Debian service behavior; schedule that work
appropriately. Neither playbook changes the firewall or public DNS.

## Generate and protect the database credential

Generate a secret through the service's linked OpenSSL library:

```bash
docker run --rm --log-driver=none mailadmin:staging secret create
ansible-vault create /absolute/private/mailadmin-vault.yml
```

Without local Docker access, run the same CLI from the built Buildah image:

```bash
mailadmin_cli=$(buildah from mailadmin:staging)
buildah run --network none "$mailadmin_cli" -- /usr/local/bin/mailadmin secret create
buildah rm "$mailadmin_cli"
```

Put the generated value into the encrypted file as
`vault_mailadmin_database_password: '<generated-value>'`. Do not place it in shell
arguments, inventory committed to git, or logs. The host role requires this
64-character hexadecimal format, creates a separate `mailadmin@localhost` login
with SELECT only in inventory mode or SELECT/INSERT/UPDATE/DELETE in administration
mode, and writes the protected configuration with `no_log`. For synthetic staging,
generate a second independent secret as `vault_mailadmin_auth_database_password`
for Courier's separate SELECT-only login.
Do not reuse or change Courier's production authentication database login.

## Provision staging

```bash
ansible-playbook -i /absolute/private/inventory.yml deploy/ansible/host.yml \
  -e @/absolute/private/mailadmin-vault.yml --ask-vault-pass --limit staging
ansible-playbook -i /absolute/private/inventory.yml deploy/ansible/deploy.yml \
  --limit staging
```

The host role reserves numeric Courier IDs, installs runtime packages, prepares
restricted directories and creates a synthetic InnoDB database only if empty.
Its disabled sample accounts have no mailbox passwords. It changes authmysql only
in explicit staging mode; no production custom query or old POP login is removed.
Staging Courier authentication restarts when its managed settings change.

The deployment playbook loads the archive (or pulls `mailadmin_image` from a
registry when no archive is supplied) and installs the systemd unit. It leaves
the daemon stopped on first deployment. No API key is generated by Ansible, so
the plaintext credential cannot be captured in registered task output.

Image archives are transferred into a root-only cache directory, not the
Courier-owned daemon state directory. This prevents the mail user from replacing
an archive before the privileged Docker import.

On a fresh staging host, create a key as root in the protected credential directory. Its only plaintext
output is the new key; save it in your password manager or a protected local file:

```bash
docker run --rm --log-driver=none --read-only --cap-drop=ALL \
  --security-opt=no-new-privileges --user 0:0 \
  --mount type=bind,src=/etc/mailadmin/credentials,dst=/etc/mailadmin/credentials \
  mailadmin:staging key create --key-file /etc/mailadmin/credentials/api-key.sha256
chown root:113 /etc/mailadmin/credentials/api-key.sha256
chmod 0640 /etc/mailadmin/credentials/api-key.sha256
```

No shell or mounted config/DB credentials are needed for this CLI command. It
refuses to overwrite an existing verifier. Use `key rotate` deliberately to
replace it. The daemon reads the verifier at startup, so restart it after rotation.
Removing a key file likewise requires stopping/restarting the service to revoke
the in-memory credential. One administrator credential is supported in this
milestone; there is no key enumeration or end-user identity system.

Enable the service in the private inventory (`mailadmin_start_service: true`),
then run deployment again:

```bash
ansible-playbook -i /absolute/private/inventory.yml deploy/ansible/deploy.yml \
  --limit staging
```

API operations and metrics both require the same bearer key. Access staging over
an SSH tunnel; the default API only binds loopback:

```bash
ssh -N -L 18080:127.0.0.1:8080 root@staging.example.net
```

In another terminal on the controller, with the plaintext API key stored in a
protected file (not the `.sha256` verifier), run:

```bash
python3 tests/staging_smoke.py --url http://127.0.0.1:18080 \
  --token-file /absolute/private/staging-api-key --staging-fixture
```

The test verifies 401/405/404 behavior, readiness, organization/domain JSON and
the two required metrics. It does not mutate accounts or mail. Use
`journalctl -u mailadmin` on staging to debug operational failures; log lines
include request IDs, never authorization values or database passwords. Do not
put credentials in request paths/query parameters: HTTP access logs include URLs.

## Upgrade and repeatability

The supplied `ssh staging` VM is now provisioned and running. Its verification
results and operating commands are in [staging.md](../../doc/staging.md).

Rebuild/tag the image, replace the image archive or registry reference in inventory,
and rerun `deploy.yml`. Image identity changes or unit changes restart an enabled
daemon; persistent state, key and database remain intact. Re-running host
provisioning does not reset the staging fixture or rotate its database password
unless the Vault value is deliberately changed. Config changes restart an enabled
daemon; keep `mailadmin_start_service` true in its inventory once deployed.

## GitHub Actions image publication

`.github/workflows/container.yml` follows the yahat-cpp container workflow's
GHCR authentication pattern using the repository's `MY_PAT` secret. It builds
on relevant pushes to `main` and permits manual dispatch from `main`. Documentation
and deployment-only changes do not trigger image builds. The Dockerfile runs the
security and coroutine bridge tests before producing the runtime image.

Successful runs publish `ghcr.io/jgaa/mailadmin:latest` and
`ghcr.io/jgaa/mailadmin:sha-<full-commit-sha>`. The OCI version label is read from
root `CMakeLists.txt`; workflow files do not duplicate the application version.
Manual dispatch refreshes dependency/base layers rather than using cached RUN
layers. The workflow does not deploy to staging or touch mail-server credentials.

To deploy a registry image later, set `mailadmin_image_archive: ''` and select a
published image reference in inventory. Use its commit tag or digest for a
specific build. If GHCR visibility is private, configure a read-only registry
credential on the host separately; the CI publishing PAT is not copied to staging.

To upgrade the selected host packages rather than just ensure they are installed:

```bash
ansible-playbook -i /absolute/private/inventory.yml deploy/ansible/host.yml \
  -e @/absolute/private/mailadmin-vault.yml --ask-vault-pass \
  -e mailadmin_package_state=latest --limit staging
```

Use `--syntax-check` for controller validation. `--check --diff` can help review
changes on a prepared host (secret-bearing tasks suppress diffs). A blank host
does not yet have the database, Docker or groups required for every dry-run lookup;
check mode is not a substitute for a real disposable staging run.

## Existing server: InnoDB conversion

Run only in an agreed maintenance window after stopping legacy admin writers,
imports and other database writers. Account for mail-delivery quota updates and
Courier's password-change interfaces when establishing that window. The playbook
requires an explicit operator assertion rather than guessing which host services
it may stop:

```bash
ansible-playbook -i /absolute/private/production.yml deploy/ansible/migrate-innodb.yml \
  -e mailadmin_writers_stopped=true --limit production
```

It first takes a root-only, locked SQL dump into `/var/backups/mailadmin`, then
converts only remaining MyISAM tables and verifies all four are InnoDB. The
playbook is resumable after an interrupted conversion; it keeps each backup.
No organization-key alteration, password conversion, domain migration, config
rewrite or server restart is bundled into this operation. Test restoring the
backup on staging before production cutover. Do not restore it over a database
that has accepted newer mail/account changes without a recovery plan.

## Moving to a replacement server

Provision the OS/packages with the production inventory settings, transfer a
verified database backup and all spool metadata with numeric ownership, and
restore protected production Courier configuration/certificates separately.
Keep the host's current mail service disabled until restore and validation are
complete. The playbooks do not copy production mail or secrets to staging and
do not cut over MX records. Finish the targeted activation and authentication
checks in [mailserver.md](../../doc/mailserver.md) before switching traffic.

## Enable actual administration

See [administration and recovery](../../doc/administration.md) before upgrading
an inventory-only installation. Stop writers, back up/convert InnoDB, load the
new image, and apply the explicit schema migration before starting write mode:

```bash
ansible-playbook -i /absolute/private/inventory.yml deploy/ansible/migrate-administration.yml \
  -e mailadmin_writers_stopped=true
```

Set `mailadmin_administration: true` only after that boundary. Host provisioning
installs the restricted root publisher and timer, grants runtime DML privileges,
and keeps the JSON database credential readable only by root and the container's
administration group. Rotate the old inventory database secret before granting
write privileges. Staging authentication requires a second independently generated
Vault variable, `vault_mailadmin_auth_database_password`, for a separate
SELECT-only Courier login. Existing-server mode preserves production authmysql.
The staging fixture check counts the four legacy tables, so later administration
tables do not cause a repeat provisioning failure.

For destructive tests, copy `tests/staging_business.py` to the disposable VM and
run it as root with `--mail-protocols`. It reads the protected key file, creates
only synthetic `.test` domains/accounts, and removes its own records afterward.
Never run it against production. Runtime/SMTP/IMAP exceptions and response bodies
are suppressed because they may contain credentials.

## Deploy the Wt UI

Build the separate UI image on the controller and load it onto staging:

```bash
./deploy/build-image.sh mailadmin-ui:staging \
  "$HOME/.local/state/mailadmin/images/ui-staging.tar" Dockerfile.ui
ansible-playbook -i deploy/ansible/inventory.staging.yml deploy/ansible/deploy-ui.yml \
  --limit staging
```

This installs `mailadmin-ui.service` and starts an unprivileged container with a
read-only API-key mount and writable UI authentication state, without database/Courier access. Staging exposes the UI over HTTP on port
8081 and connects to the unchanged API over loopback HTTP on port 8080. Open
`http://192.168.1.199:8081` and sign in as `admin` with the UI password stored in
`/var/lib/mailadmin-ui/initial-password` (0600). Configure the backend key using
`mailadmin_ui_api_key_source` or `vault_mailadmin_ui_api_key`; it is never entered
in the browser or included in the unit/image. See the UI guide for password rotation. Repeat deployments
restart only the UI when its image or unit changes. See the [UI guide](../../doc/ui.md)
for browser checks with JavaScript enabled and disabled.

## Enable nsblast DNS provisioning

Use the upgraded API image and explicit schema migration before enabling DNS.
Configure `mailadmin_nsblast_api_url`, a scoped credential through
`vault_mailadmin_nsblast_api_key` or root-only `mailadmin_nsblast_api_key_source`,
and `mailadmin_default_mail_hostname`. Optional policy overrides go in
`mailadmin_dns_default_configuration`. Enabling MTA-STS additionally requires
`mailadmin_nsblast_mta_sts_https_ready` after trusted HTTPS delivery is configured.

For an existing provisioned host, `configure-dns.yml` preserves its database and
listener settings and installs the credential with container-only read access:

```bash
ansible-playbook -i deploy/ansible/inventory.staging.yml deploy/ansible/configure-dns.yml \
  --limit staging
```

Staging uses the loopback nsblast mail-test service and its existing scoped key.
The shared hostname reuses the synthetic `mail.example.test` fixture; supply the
real MX hostname in production inventory. The UI supports dedicated host addresses
as an explicit alternative. See [DNS provisioning](../../doc/dns.md) for defaults,
RFC rationale, retry/retirement behavior and verification. DNS deletion preserves
host addresses and unrelated records. No existing zones are created or removed.
